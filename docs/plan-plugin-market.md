# 분석 — 플러그인 마켓 (#202)

준영님(2026-09-21):
> *"앞으로 사내에서 만든 웹이나 이런 것들을 전부 아라를 통해서만 접속하게 해야 한다고 하더라고.
> 플러그인 마켓을 통해 여러 사람이 등록한 웹·시스템·기능들을 우리 쪽에 다운로드 받아서
> 세션 창처럼 띄우는 거야. 확장성도 있어야 하고, 어떻게 붙이는지 공통화도 해야 하고,
> electron 으로 만든 것들은 또 어떻게 붙일지도 고민해야 해."*

## 🔴 준영님 확정(2026-09-21) — 이 셋이 설계를 절반으로 줄였다

| | 결정 | 무엇이 사라졌나 |
|---|---|---|
| ① | **플러그인은 아라의 무엇에도 안 닿는다** | 능력(capability) 체계 · 전용 preload · `window.ara` — **전부 불필요** |
| ② | **등록은 누구나, 공개는 검토 후**(준영님이 병합) | 서명 체계 — 레지스트리가 **우리 리포**에 있으면 git 리뷰가 곧 검토다 |
| ③ | **`kind: web` 부터** | 받는 것이 없으니 **해시 검증·번들 스킴도 지금은 불필요** |

→ **남는 것은 "주소 목록 + 사이드바 버튼 + 아라 브라우저" 셋뿐이다.** 그게 이 기능의 P1 전부다.

## 1. 🟢 보안은 이미 다 만들어 뒀다 — 새로 설계하지 않는다

`src/main/browser/BrowserService.ts` · `BrowserTabs.ts` 가 **남의 웹을 아라 안에서 안전하게
그리는 법**을 이미 풀어 놨다. 불변식 아홉이 주석에 있고 `tests/w2-browser.cjs` 가 잰다:

- preload 미주입 · `sandbox` · `contextIsolation` · `nodeIntegration` 없음 · `webviewTag` 없음
- **전용 파티션** — 앱 쿠키·저장소와 완전 분리
- http/https 외 스킴은 **진입과 이동 양쪽에서** 차단(`will-navigate`·`will-redirect`·`will-frame-navigate`)
- 권한 요청 전부 거부 · 다운로드 차단 · 새 창 금지
- 인증서 오류 핸들러를 **등록하지 않는다**(Electron 기본값 = 거부가 그대로 산다)
- 탭 라벨에 **페이지 제목을 안 쓴다** — 오리진만

🔴 **결정 ① 덕분에 이 경계를 한 글자도 안 바꾼다.** 플러그인은 `hardenSession` +
`wireTabContents` 를 그대로 탄다. `window.ev` 도 `window.ara` 도 없다 — 플러그인이 할 수 있는
것은 **자기 서버와 통신하는 것뿐**이고, 그건 크롬에서 열었을 때와 똑같다.

---

## 2. 어디에 뜨나 — **준영님 안(사이드바 → 아라 브라우저 탭)이 맞다**

준영님 질문:
> *"사이드바에 버튼이 생기고 누르면 브라우저가 켜지고 바로 접속… 이런 게 좋을까?
> 아니면 현재 세션 창과 창을 공유해서 탭별로 독립적으로 쓰는 게 좋을까?"*

### 🔴 결정적인 이유: **플러그인은 세션이 아니다**

세션 창(F32)은 **"이 서버를 보는 화면"** 이다 — 떼어낸 탭들이 사는 곳이고, 여러 개가 뜬다.
그런데 플러그인은 서버에 매여 있지 않다. **세션 창이 셋이면 ERP 플러그인은 어디에 붙나?**
답이 없다. 셋 다에 띄우면 같은 사이트가 세 벌 뜨고, 하나만 고르면 그 창을 닫을 때 같이 사라진다.

브라우저 창은 그 질문 자체가 안 생긴다 — **앱에 하나고, 세션과 수명이 무관하다.**

### 그리고 세션 창에 넣으면 값을 치러야 한다

과거의 우리가 경고를 남겨 뒀다(`BrowserService.ts:5-7`):
> *"WebContentsView 를 메인 창에 붙이면 React 오버레이(설정 드로어·모달·컨텍스트 메뉴·검색 바)가
> 전부 그 밑에 깔려 레이아웃 코드 전역에 숨김/복원 배선을 심어야 한다."*

`WebContentsView` 는 네이티브 뷰라 창의 웹 문서 **위에** 합성된다 — HTML 로 그 위를 못 덮는다.
세션 창에도 `Dialog`·`ContextMenu`·하단 패널이 있으니 같은 값을 치른다. 그리고 그건
**"등록을 빠뜨리면 조용히 깨지는" 축**이다 — #201 이 잡고 있는 바로 그 병이다.

### ✅ 그래서: 사이드바 버튼 → 아라 브라우저 탭

```
[아라 본창]                    [A.R.A 브라우저]
 ┌──────────┬────────────┐      ┌─ERP─┬─위키─┬─CI─┐
 │ 사이드바  │  터미널     │      │              │
 │ ▸ 연결    │            │      │  ERP 관리자   │
 │ ▸ 파일    │            │      │              │
 │ ▸ 플러그인 │            │      └──────────────┘
 │   • ERP  │            │
 │   • 위키  │            │       ← 팝업도 여기 탭으로
 └──────────┴────────────┘
```

**나중에 칸으로 옮기고 싶어지면** 매니페스트가 그대로라 자리만 바꾸면 된다. 지금 정할 필요 없다.

## 3. 🔴 고쳐야 할 것 하나 — `window.open` 이 지금 **보던 페이지를 잃는다**

준영님: *"해당 사이트에 여러 창이 필요하면 아라 브라우저에서 새 창을 띄워서 브라우저 탭에 올려주고"*

지금 코드(`BrowserService.ts:63-66`):
```ts
wc.setWindowOpenHandler(({ url }) => {
  if (isSafeExternal(url)) void wc.loadURL(url)   // ← 보던 탭을 그 주소로 갈아치운다
  return { action: 'deny' }
})
```
사내 시스템은 팝업을 많이 쓴다(결재창·미리보기·달력). 지금은 그 팝업이 **보던 페이지를 덮어쓴다** —
거부보다 나쁘다. 주석이 이 날을 예고해 뒀다:
> *"ponytail: 팝업 기반 OAuth 는 이 정책에서 깨진다. … 실제로 막히면 그때 팝업을 허용한다."*

**고침**: `loadURL` 대신 **새 탭**으로 연다. 창은 여전히 안 만든다(`deny` 유지).
⚠️ 이건 플러그인만의 이야기가 아니다 — **지금 브라우저도 같이 나아진다.**

## 4. 🔴 Electron 으로 만든 것 — **붙일 수 없다. 그리고 그게 맞다**

Electron 앱은 **자기 main 프로세스 + Node + 자기 BrowserWindow** 다. 그것을 아라 안에
"붙인다"는 말은 **남이 만든 Node 코드를 아라의 권한으로 돌린다**는 뜻이고, 아라가 지켜 온
경계(명령 카탈로그 · MCP 승인 · 자유 문자열 실행 금지)를 한 번에 무효로 만든다.
기술적으로도 길이 없다: 창 재부모화(`SetParent`)는 Electron 이 지원하지 않고(크기·DPI·포커스에서
깨진다), `webview` 태그로는 다른 Electron 앱을 못 연다.

### 대신 셋 중 하나로 보낸다

| | 언제 | 무엇을 하나 |
|---|---|---|
| **C1 화면만 떼어낸다** | **대부분 여기다** | Electron 앱의 **화면은 이미 웹이다.** 그 렌더러를 사내 서버에 올리면 그 순간 **`kind:web` 플러그인**이다. 결정 ① 덕분에 아라가 줄 것도 없다 — `ipcRenderer` 쓰던 자리만 자기 서버 API 로 바꾸면 된다 |
| **C2 진짜 Node·네이티브가 필요** | 파일 접근·네이티브 모듈·OS 제어 | 그건 **화면이 아니라 기능**이다. 그 부분을 서버·로컬 데몬으로 빼고 화면은 C1 로 |
| **C3 도저히 안 된다** | 레거시·외주 | 마켓에 **"외부 앱"** 으로 올리고 아라는 **띄우기만** 한다(`shell.openPath`) |

⚠️ **C3 를 조용히 숨기지 않는다.** "아라를 통해서만"이 목적인데 아라가 남의 exe 를 띄우는 것을
"아라 안"인 척하면 나중에 감사에서 문제가 된다. 목록에 *"아라 밖에서 열립니다"* 를 적는다.

## 5. 공통화 = 매니페스트 한 장 (결정 ①~③ 반영 — 훨씬 작아졌다)

```jsonc
{
  "id": "vgt-erp-admin",          // 고유. 저장소·설정 키가 여기서 파생
  "name": "ERP 관리자",            // 🔴 사이드바·탭 라벨. 레지스트리가 출처라 **위장이 아니다**(§6)
  "icon": "erp.svg",
  "kind": "web",                  // web | external
  "publisher": "개발1팀",          // 사람이 볼 책임 소재
  "url": "http://erp.사내/admin",
  "origins": ["http://erp.사내"], // 🔴 이 밖으로 나가면 라벨이 오리진으로 떨어진다
  "group": "업무",                 // 사이드바 묶음
  "minAraVersion": "1.3.0"
}
```

**없는 것**(결정 ① 덕분): `capabilities` · `sha256` · `entry` · `ai`.
필요해지는 날 **그때** 더한다 — 지금 넣으면 아무도 안 쓰는 필드가 표준이 된다.

## 6. 탭 라벨에 이름을 써도 되는 이유 — 레지스트리가 신뢰 기준점이다

지금 브라우저는 **페이지 제목을 안 쓰고 오리진만** 쓴다. 원격 페이지가 "A.R.A 설정" 이라는 이름의
탭으로 앉는 것을 막기 위해서다. 플러그인은 다르다 — **이름의 출처가 페이지가 아니라 레지스트리**이고,
그건 준영님이 검토해 병합한 것이다(결정 ②).

🔴 **단, 선언한 `origins` 안에 있을 때만.** 그 밖으로 이동하면 **오리진 표기로 떨어진다** —
안 그러면 플러그인이 아무 사이트로 이동해 놓고 "ERP 관리자" 라는 이름을 달고 있게 된다.
이 규칙이 §5 의 `origins` 필드가 존재하는 이유 전부다.

## 7. ⚠️ 먼저 정해야 할 것 하나 — 사내 SSO 를 공유하나

파티션을 어떻게 나누느냐가 **로그인 횟수**를 정한다.

| | 어떻게 | 결과 |
|---|---|---|
| **공유** `persist:ara-plugins` | 플러그인 전부가 쿠키를 공유 | 사내 SSO 를 한 번만 로그인. ⚠️ A 플러그인이 B 의 쿠키를 본다 |
| **분리** `persist:ara-plugin-<id>` | 플러그인마다 자기 쿠키 | 격리는 완벽. ⚠️ **같은 SSO 인데 플러그인마다 다시 로그인** |

사내 시스템이 SSO 를 공유한다면 분리는 매번 로그인을 강요해 **아무도 안 쓰게 된다.**
반대로 공유는 "사내 시스템끼리는 서로 신뢰한다"는 가정이다 — 사내 전용이고 검토를 거치니
합리적이다. **권고: 공유를 기본으로, 매니페스트에 `isolated: true` 로 빼는 길만 열어 둔다.**
(⚠️ 아라 본체 세션과는 **여전히 완전 분리**다. 이 이야기는 플러그인들 사이에서만이다.)

## 8. 마켓 = 리포 안의 `registry.json` — 서버를 새로 만들지 않는다

결정 ②(공개는 검토 후)가 서명 문제를 통째로 없앤다:

```
site/plugins/registry.json      ← 🔴 **우리 리포 안**. 등록 요청 = PR, 검토 = 코드 리뷰
```
`npm run site:deploy` 가 사이트를 올릴 때 **같이 올라간다**(`scripts/deploy-site.mjs`).
아라는 `http://192.168.100.56:8899/plugins/registry.json` 을 읽는다.

- **서명 불필요** — 레지스트리를 만드는 것도 배포하는 것도 우리다
- **해시 불필요** — `kind:web` 은 받는 것이 없다(주소만 읽는다)
- ⚠️ 평문 HTTP 라 사내망에서 가로채면 **주소를 바꿔치기할 수 있다.** 자동 업데이트가 이미
  같은 약점이고 `docs/tasks.md` 보류 표에 있다. 🔴 **`kind:bundle` 을 시작하는 날
  이 문제를 먼저 풀어야 한다**(받은 코드가 우리 PC 에서 돌기 시작하므로).

# 부록 — 프록시로 묶기 (2026-09-21 준영님 제안)

> *"배포 서버에 8000~9000 사이만 외부 포트로 열려 있어. 다른 시스템들은 그 외 포트(내부 전용)를
> 쓰고 우리가 서버를 하나 두고 프록시 형태로 제공하는 건 어때? 그러면 외부에서는 그 서버에
> 접속이 불가하지만 우리 쪽만 들어갈 수 있잖아."*

**방향은 맞다.** 들어오는 문을 하나로 모으면 인증·감사·플러그인 목록이 한자리에 온다.
그리고 caddy 가 **이미 그 서버에 돌고 있다**(`scripts/deploy-site.mjs:14`) — 새로 세울 것이 없다.

## 🔴 그런데 전제 하나가 틀렸다 — 프록시는 숨기는 장치가 아니다

> *"외부에서는 그 서버에 접속이 불가하지만"*

프록시를 8899(외부에 열린 포트)에 두는 순간 **8899 에 닿는 사람은 그 뒤의 시스템 전부에 닿는다.**
포트를 안 연 것이 "못 들어온다"가 아니라 **"문이 하나로 줄었다"** 는 뜻이다.
오히려 지금까지 사내망에서만 보이던 시스템이 그 문을 통해 **밖에서 보이게 된다** — 노출이 는다.

🔴 **보안은 포트가 아니라 그 문에서 누구인지 확인하는 데서 나온다.**

## 그런데 그게 오히려 기회다 — *"아라를 통해서만"* 을 정책이 아니라 강제로

프록시가 **아라만 가진 자격**을 요구하게 하면, *"아라를 통해서만 접속"* 이 사람에게 부탁하는 말이
아니라 **기술적으로 참인 문장**이 된다. 크롬 주소창에 쳐도 401 이다.

| 수단 | 막는 것 | 못 막는 것 |
|---|---|---|
| **토큰 헤더** — 아라 브라우저의 `WebContentsView` 에 `onBeforeSendHeaders` 로 붙인다(≈5줄) | "크롬으로 그냥 들어가기" | 앱을 뜯어 토큰을 꺼낸 사람 |
| **mTLS(클라이언트 인증서)** | 같음 + 네트워크 도청 | 같음 |
| **사람 로그인(SSO)** | **권한 없는 사람** | — |

🔴 **앱에 심은 비밀은 비밀이 아니다.** 사내 배포는 무서명이라 누구나 `app.asar` 를 연다.
그러니 둘을 **섞어 말하면 안 된다**:
- *"실수로/편하다고 크롬에서 접근"* 을 막는 것 → **토큰이면 충분하다**(대부분 여기가 목적일 것이다)
- *"권한 없는 사람"* 을 막는 것 → **사람 인증이 필요하다.** 프록시로는 안 된다

## 🔴 진짜 갈림길 — 경로냐 서브도메인이냐

| | 경로 `…:8899/p/erp/` | 서브도메인 `erp.ara.사내:8899` |
|---|---|---|
| **절대경로** | 🔴 **깨진다.** ERP 가 `/static/app.js` 를 부르면 프록시 루트로 가서 404. 사내 앱 대부분이 base path 를 지원 안 한다 — **경로 프록시의 제1 사망 원인** | 안 깨진다 |
| **오리진** | 🔴 **전부 한 오리진이 된다.** A 플러그인이 B 의 쿠키·localStorage 를 읽고 B 에 인증된 요청을 보낸다. §7 의 "공유냐 분리냐" 선택지가 **아예 사라진다** | 갈린다. SSO 쿠키는 상위 도메인으로 공유 가능 — **§7 을 고를 수 있다** |
| **필요한 것** | 없음 | **DNS 와일드카드** `*.ara.사내 → 192.168.100.56` |
| **포트** | 하나 | 하나 (caddy 가 `Host` 헤더로 가른다) |

**권고: 서브도메인.** DNS 한 줄이 경로 재작성 지옥보다 싸고, 오리진 경계를 잃지 않는다.
DNS 를 못 건드리면 경로로 가되 **§7 의 격리를 포기한다는 것을 명시적으로 적는다.**

## 값이 있는 곳은 "숨기기"가 아니라 여기다

- **감사 로그** — caddy access log 가 *"누가 언제 무엇을 열었나"* 를 공짜로 준다.
  *"아라를 통해서만"* 을 요구한 진짜 이유가 아마 이것이다
- **등록이 한 번으로 끝난다** — 레지스트리가 리포에 있으므로(§8) **등록 PR 하나가
  ① 아라 플러그인 목록 ② caddy 라우트 를 함께 만든다.** 두 벌이 안 된다
- 포트를 하나씩 나눠 주는 것과 비교하면, 프록시의 값은 **인증·감사를 한자리에 모으는 것**이지
  숨기는 것이 아니다(8000~9000 은 1001개다 — 숨기는 게 목적이면 프록시가 필요 없다)

## ⚠️ 치러야 할 값

- **단일 장애점** — 프록시가 죽으면 **아라 자동 업데이트까지** 같이 죽는다(같은 caddy 다).
  업데이트 채널만은 라우트를 갈라 두는 것을 권한다
- **caddy 를 Caddyfile 로 바꿔야 한다** — 지금은 `caddy file-server --root /srv` 명령 한 줄이다
  (`deploy-site.mjs:97`). 프록시를 얹으려면 Caddyfile 하나 + 그 줄 수정
- **Range 요청이 살아 있어야 한다** — 업데이트 차등 다운로드(blockmap)가 그 위에서 돈다.
  caddy 를 고른 이유가 그것이다(`deploy-site.mjs:16`). 프록시로 바꾸며 이걸 깨면 **매번 92MB** 다
- **WebSocket·SSE** — caddy `reverse_proxy` 는 기본 통과한다(nginx 였으면 설정이 필요했다)

## 먼저 답이 필요한 것

1. **"외부"가 인터넷인가, 다른 사내 대역인가?** 인터넷이면 인증 없는 프록시는 **지금 당장 위험**하다
2. **DNS 와일드카드를 만들 수 있나?** 이 한 줄이 위 표의 승자를 정한다
3. 프록시로 막고 싶은 것이 *"크롬으로 그냥 들어가기"* 인가, *"권한 없는 사람"* 인가

## 준영님 답(2026-09-21)으로 확정된 것

| 물음 | 답 | 결과 |
|---|---|---|
| "외부"가 어디인가 | **사내 다른 개발자 PC** | 인터넷 노출이 아니다 — 위 §"전제가 틀렸다"의 **위험도가 크게 내려간다** |
| DNS 와일드카드 | **개발 불가** · 운영은 추후 **SSL 와일드카드 있음** | 개발은 서브도메인을 못 쓴다. 운영은 나중에 쓸 수 있다 |
| 무엇을 막나 | **"크롬으로 그냥 들어가기"** | 사람 인증이 아니라 **문패**면 된다 |

## ✅ 답: **포트 기반 프록시** — DNS 없이 오리진을 가르는 유일한 길

경로 기반의 두 사망 원인(절대경로·오리진 붕괴)을 **포트가 둘 다 푼다**:

```
개발자 PC ──┐
            │  8000~9000 만 열림
            ▼
  192.168.100.56
   :8899  ara-site    (다운로드·업데이트·registry.json)   ← 토큰 없음
   :8901  ara-proxy ──→ localhost:3000  ERP     ← 실서비스는 막힌 포트
   :8902  ara-proxy ──→ localhost:5000  위키
   :8903  ara-proxy ──→ localhost:7000  CI
```

- **절대경로가 안 깨진다** — 플러그인이 자기 포트의 **루트**(`/`)에 앉는다
- **오리진이 갈린다** — `host:8901` 과 `host:8902` 는 다른 오리진이다(localStorage·IndexedDB·
  같은-오리진 판정이 전부 갈린다)
- **DNS 가 필요 없다**
- 🔴 **우회가 불가능하다** — 실서비스 포트(3000·5000…)는 방화벽에 막혀 있어 개발자 PC 에서
  직접 못 닿는다. 프록시만이 길이다. 이게 *"아라를 통해서만"* 의 **구조적** 부분이다

### ⚠️ 포트로는 안 갈리는 것 하나 — 쿠키

**쿠키는 호스트 기준이고 포트를 무시한다.** `host:8901` 이 심은 쿠키를 `host:8902` 도 본다.

| | 갈리나 |
|---|---|
| `localStorage` · `sessionStorage` · IndexedDB | ✅ 갈린다 |
| 같은-오리진 판정(fetch·DOM 접근) | ✅ 갈린다 |
| **쿠키** | ❌ **안 갈린다** |

→ **SSO 에는 편하고**(한 번 로그인하면 전부 통한다 — §7 의 "공유"가 저절로 된다),
격리로는 **구멍이다**(HttpOnly 면 JS 가 읽진 못하지만 요청에는 실려 나간다).
사내 전용 + 검토 후 공개(결정 ②)라 **받아들일 만하다. 다만 모르고 있으면 안 된다.**

### 운영으로 갈 때 — 데이터만 바뀐다

운영에 SSL 와일드카드가 생기면 `https://erp.사내/` 식 **서브도메인**으로 옮긴다.
매니페스트의 `url`·`origins` 만 바뀌므로 **아라 코드는 한 줄도 안 바뀐다.**
🔴 그러니 **포트 기반을 코드에 새기지 않는다** — 주소는 레지스트리에만 산다.

## 문패 — "크롬으로 그냥 들어가기" 막기

목적이 사람 인증이 아니라 **"아라로 여세요"** 이므로 토큰 하나면 된다.

**caddy 쪽** (새 `ara-proxy` 컨테이너, `--network host`):
```caddyfile
{ auto_https off }

(ara_only) {
	@notara not header X-ARA-Token "<공유 비밀>"
	respond @notara "아라에서 열어 주세요 — http://192.168.100.56:8899/" 403
}

:8901 {
	import ara_only
	reverse_proxy localhost:3000        # ERP
	log { output file /var/log/caddy/erp.log }     # ← 감사 로그가 여기서 공짜로 나온다
}
```
⚠️ `--network host` 를 쓰는 이유: 안 쓰면 플러그인이 하나 늘 때마다 `-p` 를 더해
**컨테이너를 다시 만들어야** 한다. host 면 Caddyfile 한 줄 + reload 다.

**아라 쪽** — 플러그인 파티션에만, **호스트를 확인하고** 붙인다:
```ts
ses.webRequest.onBeforeSendHeaders((d, cb) => {
  // 🔴 호스트를 콜백에서 직접 본다. 매치 패턴에 맡기면 토큰이 남의 사이트로 샌다.
  const host = new URL(d.url).hostname
  cb(host === PROXY_HOST ? { requestHeaders: { ...d.requestHeaders, 'X-ARA-Token': TOKEN } } : {})
})
```

🔴 **이건 잠금이 아니라 문패다.** 사내 배포는 무서명이라 누구나 `app.asar` 를 열어 토큰을 꺼낸다.
*"크롬으로 그냥 들어가기"* 를 막는 데는 충분하고 — **준영님이 원하신 게 그것이다.**
"권한 없는 사람"까지 막으려면 그때는 사람 인증(SSO)이고, 그건 다른 일이다.

## 🔴 반드시 열어 둬야 하는 것 — 안 그러면 아라를 처음 받을 길이 없다

| 자리 | 토큰 | 왜 |
|---|---|---|
| `:8899/` 다운로드 페이지 | **없음** | 아라가 없는 PC 가 크롬으로 받으러 온다. **닭과 달걀** |
| `:8899/downloads/` | **없음** | `electron-updater` 는 그 헤더를 안 보낸다. 걸면 **자동 업데이트가 죽는다** |
| `:8899/plugins/registry.json` | 없음(무방) | 주소 목록일 뿐이다 |
| `:890x` 플러그인 | **있음** | 여기만 막으면 된다 |

## 컨테이너를 **둘로** 나눈다 — 아까 걱정한 단일 장애점이 이걸로 없어진다

- **`ara-site`(기존, 8899)** — 손대지 않는다. 배포·업데이트가 그 위에서 도는 검증된 경로다
  (Range 요청이 살아 있어야 차등 다운로드가 된다 — `deploy-site.mjs:16`)
- **`ara-proxy`(신규)** — 플러그인 라우트만. 죽어도 **아라 업데이트는 멀쩡하다**

`deploy-site.mjs:94` 의 기존 `docker run` 은 **한 글자도 안 고친다.** 프록시는 별도 스크립트다.

# 부록 2 — 자율 등록("npm 처럼", 2026-09-21 준영님)

> *"다른 개발자가 웹 서비스를 개발하면 8000~9000 이 아닌 포트에 올리고, 우리 ara-proxy 사이트에
> 접속해서 연결할 포트를 우리 아라에 연결하는 거지. 즉 npm 처럼. 우리는 아라 브라우저를 통해
> 프록시 서버에 등록된 서버로 라우팅 해 주고."*

**그게 맞는 끝 그림이다.** 등록 서버가 레지스트리의 진실이 되고, 아라는 그것을 읽어 그린다.
다만 **PR 방식(§8)과 두 벌로 두지 않는다** — 등록 사이트는 *같은 `registry.json` 을 쓰는
또 하나의 작성자*여야 한다. 형식이 하나면 순서는 나중에 바꿔도 안 버려진다.

## 🔴 먼저 — 자율 등록은 방금 세운 보안 성질을 **무너뜨린다**

포트 기반 프록시가 값을 갖는 이유는 이것 하나였다:

> *"실서비스 포트는 방화벽에 막혀 있어 개발자 PC 에서 직접 못 닿는다. 프록시만이 길이다."*

그런데 **아무나 임의의 포트를 등록할 수 있으면, 방화벽이 막아 둔 것을 프록시가 열어 준다.**
등록한 포트가 자기 서비스라는 보장이 어디에도 없다:

| 등록해 버리면 | 결과 |
|---|---|
| `localhost:22` | SSH 가 8000~9000 을 통해 노출 |
| `localhost:3306` · `5432` | DB 가 노출 |
| `localhost:2375` · 도커 소켓 앞단 | **서버 장악** |
| 남의 서비스 포트 | 그 사람 것을 내 이름으로 |

이건 SSRF 계열의 전형적인 사고다. **자율 등록을 붙이는 날 이것부터 푼다.**

### ✅ 막는 법 — 포트 소유 증명(도메인 소유 증명과 같은 방식)

등록 요청을 받으면 서버가 **그 포트에 직접 물어본다**:

```
1. 등록 화면이 난수 토큰을 발급    →  ARA-VERIFY-9f3c…
2. 개발자가 자기 서비스에 한 줄 추가:
     GET /.well-known/ara-verify  →  그 토큰을 그대로 돌려준다
3. 서버가 localhost:<포트>/.well-known/ara-verify 를 쳐서 대조
4. 맞으면 등록, 아니면 거절
```

**SSH·DB·도커 API 는 이걸 못 돌려준다.** 웹 서비스만 통과한다 — 그게 이 관문의 전부다.
⚠️ 그리고 **허용 포트 대역을 따로 정한다**(예: 3000~3999). 22·3306·5432·2375 는 대역 밖이라
증명을 시도할 기회조차 없다. **두 겹을 다 건다** — 증명만 믿으면 미래의 어떤 서비스가
그 경로를 우연히 구현했을 때 뚫린다.

⚠️ 검토(결정 ②)는 **그대로 남긴다.** 증명은 *"그 포트가 웹 서비스인가"* 만 답한다 —
*"이게 사내 목록에 올라도 되는 물건인가"* 는 사람이 본다. 등록하면 **승인 대기**, 준영님이
누르면 라우트가 생기고 목록에 뜬다.

## ⚠️ 상태가 생긴다 — 지금 배포는 무상태다

`deploy-site.mjs:92` 주석: *"컨테이너는 매번 지우고 다시 만든다 — **상태가 없다**
(읽기 전용 마운트 하나가 전부)."*

등록 목록은 **상태다.** 지금 배포 절차에 그대로 얹으면 **배포할 때마다 등록이 날아간다.**
→ 등록 데이터는 `ara-site` 밖, 서버의 별도 볼륨에 둔다. `ara-site` 는 지금처럼 무상태로 남긴다.

## 라우트를 동적으로 — caddy admin API

새 등록마다 Caddyfile 을 고쳐 `reload` 하는 대신, caddy 의 **admin API** 로 라우트를 넣는다
(파일 편집도 재기동도 없다). 등록 서비스가 승인 시 그 API 를 한 번 부른다.
⚠️ admin API 는 기본이 `localhost:2019` 다 — **절대 밖으로 내보내지 않는다.**
그 API 에 닿으면 라우트를 아무 데나 걸 수 있으므로 위 §의 모든 방어가 무의미해진다.

## 살아 있나 — 등록은 **돌고 있는 서비스**를 가리킨다

npm 과 다른 점이 여기다. npm 은 **산출물**을 올리지만 이건 **띄워 둔 서비스**를 가리킨다.
그 서비스가 꺼지면 목록은 거짓말이 된다.
→ 등록 서비스가 주기적으로 `/.well-known/ara-verify` 를 다시 쳐서 **꺼짐/켜짐을 목록에 표시**한다
(증명에 쓴 그 경로를 그대로 재사용한다 — 두 벌을 만들지 않는다).
아라 사이드바에도 그 점이 그대로 온다. **안 그러면 눌렀는데 빈 화면이 뜬다.**

## 🔴 설계를 가르는 질문 하나 — 서비스가 **어디서** 도나

| | 서비스가 `192.168.100.56` 위에서 돈다 | 서비스가 **개발자 PC** 에서 돈다 |
|---|---|---|
| 프록시 대상 | `localhost:3000` | `192.168.100.77:3000` |
| 방화벽 | 🟢 막혀 있어 **프록시만이 길** | 🔴 같은 LAN 이라 **다른 PC 가 직접 닿는다** — 우회 불가 성질이 사라진다 |
| 수명 | 서버가 살아 있는 한 | **PC 를 끄면 죽는다** |
| 성격 | 사내 포털 | 개발 중 미리보기 |

위 설계는 **왼쪽**을 전제로 썼다. 오른쪽이면 프록시의 값은 "우회 불가"가 아니라
**"주소를 외우지 않아도 되는 것 + 감사 로그"** 로 줄어든다(그것도 값이지만 다른 값이다).

## 순서 권고 — 형식을 먼저, 서비스를 나중에

| | 무엇 | 왜 |
|---|---|---|
| **P1** | `registry.json` 을 **PR 로** 등록 + 아라 사이드바 + 프록시 라우트 손으로 | **코드 0줄짜리 등록**으로 아라 쪽을 먼저 돌린다. 매니페스트에 진짜 무엇이 필요한지 **첫 서비스 셋에서 배운다** |
| **P2** | **등록 사이트** — 포트 소유 증명 · 허용 대역 · 승인 대기 · caddy admin API · 살아 있나 확인 | 형식이 P1 과 같으므로 앞 단계가 안 버려진다. 위 방어를 설계할 시간이 생긴다 |

🔴 **거꾸로 하지 않는다.** 등록 사이트를 먼저 만들면 "무엇을 등록해야 하는지"를 모른 채
스키마를 굳히게 되고, 그 스키마가 곧 표준이 된다.
