## 1. 포지셔닝 영역 (Stage 1) — 5개

### P1. 기능 — "서버 앞에서 가장 가벼운 AI 작업대"
- **Statement**: 서버에 붙고, AI 에게 맡기고, 결과를 보는 데까지 가장 짧은 길.
- **Why true**: SSH 터미널·에이전트 탭·브라우저가 한 흐름. 사내 사용자 다수가 서버 작업 중심. "빠릿·가벼움"이 가치 축.
- **What this rejects**: 모든 걸 넣은 무거운 IDE(VS Code·JetBrains 류), 설정이 먼저인 도구.
- **Risk**: 속도는 가장 베끼기 쉽다. 기능 하나 느려지면 주장이 무너진다.

### P2. 감정·정체성 — "혼자 서버 앞에 앉아 있지 않다"
- **Statement**: 얼굴과 목소리가 있는 동료와 함께 일하는 개발자를 위한 도구.
- **Why true**: ARA 는 음성·얼굴 있는 AI 동료로 설계됨. 이름이 곧 AI 의 이름(제품명 = AI명).
- **What this rejects**: 자동완성·명령 도구로서의 AI, 익명의 "Assistant".
- **Risk**: 의인화가 유치하거나 불편해질 수 있다. 동료가 실수하면 감정적 실망이 크다.

### P3. 적수 — "보여 주되 끼어들지 않는다 (Present, not pushy)" ← Sonar 세션 제안
- **Statement**: 사람과 AI 가 같은 창을 함께 보지만, 운전대는 언제나 사람에게 있다. 검은 상자 자율 에이전트의 반대편.
- **Why true**: AI 는 자기 Space 에서만 일하고 포커스를 뺏지 않는다. 위험한 일은 승인 카드. 사용자가 가리켜 요청. AI 작업은 옅은 베일로 보인다. 화면에 AI=인디고·사람=앰버 신호가 이미 있다(시안 C).
- **What this rejects**: AI 를 마법처럼 포장(반짝이·구슬·"다 해 드려요"), 사람을 구경꾼으로 만드는 블랙박스 에이전트, 챗봇 사이드바를 덧붙인 브라우저, 주의를 빼앗는 알림·과한 움직임, 감시·추적 느낌.
- **Risk**: 경쟁자에 기대어 정의된다. 에이전트가 정말로 끼어드는 버그 하나가 주장 전체를 거짓으로 만든다.

### P4. 최초(사내) — "사람과 AI 가 같은 브라우저를 함께 보는, 회사 안의 첫 작업장"
- **Statement**: 작업대(ARA)와 창(Sonar)을 짝으로 가진 사내 최초의 공동 작업 도구.
- **Why true**: 두 제품이 처음부터 짝으로 설계됨. 사내 배포·DLP 환경을 전제로 함.
- **What this rejects**: 바깥 SaaS 에 코드를 보내는 도구, 하나짜리 AI 앱.
- **Risk**: "최초"는 회사 안에서만 방어된다. 외부 도구(Cursor·Orca 류)에 같은 기능이 생기면 근거가 얇아진다.

### P5. 세계관 — "도구는 정직하고, 사람이 주인이다"
- **Statement**: 도구는 자기가 무엇을 하는지 숨기지 않고, 결정은 사람이 한다.
- **Why true**: 사람/AI 신호색 분리, 승인 카드, 회사 밖으로 나가지 않는 보안(DLP 준수). Sonar 세션이 가족 공유 태도로 같은 말을 냄.
- **What this rejects**: "AI 가 알아서", 편의를 위해 데이터를 밖으로 보내는 것, 기능을 숨긴 매끈함.
- **Risk**: 말이 아니라 살아야 한다. 하나라도 몰래 하는 기능이 생기면 위선이 된다.

### 추천 (수렴)
**P3 를 주 영역, P5 를 그 밑의 믿음**으로. P3 는 "누가 하고 있나"가 보이는 화면 규칙으로 이미 증명되고 있고, P5 는 ARA·Sonar 둘이 공유할 수 있는 태도다. P1 은 증거(속도)로 뒷받침할 뿐 영역으로 내세우지 않는다. P2 는 ARA 단독의 성격(얼굴·목소리)으로 남긴다.

ARA·Sonar 확정. 스킬의 6기준 중 확인 안 한 것만 적어 둔다: **상표·도메인 확인 안 함**(사내 도구라 우선순위 낮음). "Sonar" 는 SonarSource(SonarQube) 와 개발 도구 범주에서 겹친다 — 사외 공개 시 확인 필요.

## 3. 무드 방향 (Stage 3) — 4개

> 네 방향은 디자이너가 서로 전혀 다른 결과를 내도록 갈랐다: 차가운 종이·선(M1) / 먹·붓(M2) / 정밀 기구(M3) / 둥글고 다정함(M4). 모든 방향에서 **브랜드색은 화면 신호색(인디고~스카이, 앰버)과 겹치지 않게** 잡았다.

### M1. 해도와 측량 (Hydrographic Survey)
- **형용사**: 측량하는 · 고요한 · 좌표 위의 · 깊이를 아는
- **색 영역**: 차가운 회백 종이 + 먹에 가까운 짙은 남회색 선. 신호색 하나 = **해도 마젠타**(해도에서 주의 표기에 쓰는 자홍). 채도 낮음, 마젠타만 튐. 다크에서는 종이↔먹 반전.
- **글꼴 영역**: 기술 도면 같은 좁은 그로테스크 + 숫자가 고른 모노. 무료 예: IBM Plex Sans KR, IBM Plex Mono.
- **이미지·아이콘**: 등심선·측심 숫자·좌표 격자. 사진 없음. 아이콘은 가는 단일 굵기 선, 직각 끝.
- **레퍼런스**:
  - NOAA Office of Coast Survey 해도 — https://nauticalcharts.noaa.gov — 정보 밀도를 조용히 다루는 법, 마젠타 하나로 주의를 거는 법
  - Ordnance Survey — https://www.ordnancesurvey.co.uk — 지도 기관의 절제된 정체성
  - swisstopo — https://www.swisstopo.admin.ch — 등고선 표현의 정밀함
  - Field Notes — https://fieldnotesbrand.com — 측량 수첩 같은 실용 인쇄물 감각
- **What this rejects**: 레이더 스윕·음파·잠수함 같은 바다 직역, 네온 사이버, 그라데이션 깊이 표현.
- **나올 마크(말로만)**: **열린 곡선 하나** — 끝이 닫히지 않은 등심선 한 줄. 두께 변화 없는 단일 선.
- **주의**: Sonar 세션은 "바다·음파 직역 금지". 이 방향은 바다가 아니라 **측량 종이**에서 가져왔지만 경계가 가깝다.

### M2. 먹과 한 획 (Ink Stroke)
- **형용사**: 단호한 · 손의 · 한 번에 쓰는 · 숨이 있는
- **색 영역**: 먹 검정 + 한지 미색, 신호색 하나 = **인주 주홍**(도장 빨강). 매우 높은 명암 대비, 중간색 거의 없음.
- **글꼴 영역**: 명조·바탕 계열 한글 + 붓 손글씨는 마크에만. 무료 예: Gowun Batang, Nanum Brush Script(예시용).
- **이미지·아이콘**: 먹 번짐·마른 붓 자국, 여백이 큰 구성. 아이콘은 붓 끝 맛이 살짝 남은 굵은 선.
- **레퍼런스**:
  - 설화수 — https://www.sulwhasoo.com — 한국 전통 재료를 현대 브랜드로 옮긴 절제
  - 국립한글박물관 — https://www.hangeul.go.kr — 한글 획 자체를 정체성으로
  - 안그라픽스 — https://www.ag.co.kr — 한국 타이포그래피의 현대적 쓰임
  - 리움미술관 — https://www.leeum.org — 검정·여백 중심의 현대 기관 정체성
- **What this rejects**: 매끈한 벡터 기하, 실리콘밸리 테크 문법, 장식적 "한국풍"(태극·단청 문양).
- **나올 마크(말로만)**: **한 획 붓 마크** — 펜(붓)이 한 번도 떨어지지 않은 획 하나. 시작은 눌리고 끝은 갈라짐.
- **주의**: 한 획 곡선은 Nike swoosh·Claude 손그림 별과 가장 가까운 영역이다. 획의 **방향·끝 모양**으로 실루엣을 갈라야 한다.

### M3. 정직한 기구 (Honest Instrument) ← Sonar 세션 의견, 강한 후보
- **형용사**: 정직한 · 손에 맞는 · 조용히 정밀한 · 위트 한 방울
- **색 영역**: 잉크 + 따뜻한 흰 종이(다크에선 따뜻한 먹), **신호색 하나**(브랜드 전용, 화면 신호색과 분리 — 예: 기구의 전원 스위치 같은 빨강 계열 후보). 넓은 면은 무채색.
- **글꼴 영역**: Pretendard + JetBrains Mono, 굵기 400/500 만. (Sonar 세션 제안 그대로)
- **이미지·아이콘**: 제품 사진처럼 정면·평탄한 빛, 버튼·눈금·스위치 같은 물리적 부품 은유. 아이콘은 둥근 cap 단일 굵기.
- **레퍼런스(태도만, 형태 복제 금지)**:
  - Braun (디터 람스) — https://www.braun-audio.com — "적을수록 낫다", 기능이 형태를 정함
  - Leica — https://leica-camera.com — "보는 도구"의 품격 (Sonar 의 축)
  - MUJI — https://www.muji.com — 내용이 주인공, 브랜드는 물러섬
  - Teenage Engineering — https://teenage.engineering — 기능 + 위트 (ARA 의 축)
  - Linear — https://linear.app — 조용한 정밀, 다크 작업 도구의 마감
- **가족 구조**: 같은 공방에서 나온 **공구(ARA)와 광학 기구(Sonar)**.
  - ARA = 작업대, "만든다": 촘촘·다크·빠른 템포·키보드, 단단함/밀도/몰입 (TE·Linear 다크)
  - Sonar = 창, "본다": 여백·글라스·느린 템포·시선, 투명/평온/관찰 (Leica·Braun·Muji)
  - 공유: 태도("도구는 정직, 사람이 주인"), 재료(잉크·따뜻한 흰 종이·신호색 하나), 활자, 모션(일할 때만, 넘침 없음), 마감 정밀도
- **What this rejects**: OpenAI·Gemini·Copilot 류 AI 브랜드 문법(반짝이·구슬·그라데이션), 게이밍 네온, 바다·잠수함·레이더·음파 직역, 감시 느낌.
- **나올 마크(말로만)**: **기하 형태 하나 + 기능적 절개 하나** — ARA 는 꽉 찬 단단한 형태(면), Sonar 는 열린·투명한 형태(테두리 또는 빈 속). 둘의 실루엣 대비가 곧 가족 규칙.
- **주의**: 따뜻한 흰 종이 + 절제는 요즘 "AI 기본 취향"과 가깝다. 차별은 마크의 위트와 마감 정밀도에서만 나온다.

### M4. 다정한 둘 (Duet)
- **형용사**: 다정한 · 말을 거는 · 둥근 · 장난기 있는 · 둘이서
- **색 영역**: 따뜻하고 채도 중간 — **산호 분홍 + 이끼 녹색 + 크림 바탕**. 다크에서는 짙은 자두색 바탕. 대비보다 조화.
- **글꼴 영역**: 둥근 고딕 한글 + 둥근 산세리프. 무료 예: Jua, Nunito.
- **이미지·아이콘**: ARA 의 얼굴·표정을 캐릭터 일러스트로, 두 형태가 대화하는 장면. 아이콘은 통통한 면 위주.
- **레퍼런스**:
  - Mailchimp — https://mailchimp.com — 위트 있는 일러스트로 도구를 친근하게
  - Headspace — https://www.headspace.com — 둥근 형태·따뜻한 색으로 안심시키는 법
  - Duolingo — https://www.duolingo.com — 캐릭터가 곧 브랜드
  - Arc (The Browser Company) — https://arc.net — 브라우저를 다정하게 만든 사례
- **What this rejects**: 차갑고 진지한 개발 도구 문법, 다크+네온, 기계적 기하.
- **나올 마크(말로만)**: **두 형태가 맞물린 덩어리 하나** — 평면 단색, 내부에 음각 하나(그라데이션 구슬 금지).
- **주의**: 사내 서버 작업 도구로는 가벼워 보일 수 있다. 다크 위주 사용 환경과 상성이 가장 나쁘다.

### 각 마크가 "Gemini·Claude·GPT·Nike 수준의 단일 고유 마크"가 되려면 (공통 조건)
1. **실루엣만으로 구별**: 검은 덩어리로 칠해 16px 로 줄였을 때 다른 마크와 헷갈리지 않는다. 비교군: Gemini 네 갈래 별, Claude 방사형 별, GPT 매듭, Nike swoosh, Windows 로딩 링, Chrome.
2. **단색 성립**: 한 색으로 찍어도 의미가 같다. 색·그라데이션은 큰 장식 변형에서만.
3. **구성 규칙이 있다**: 곡선 반경·굵기·각도가 숫자로 설명된다(우연한 손맛도 규칙으로 고정).
4. **요소는 둘 이하**: 16px 에서 2px 미만 선, 3요소 이상, 내부 글자 금지.
5. **동작과 이어진다**: 정적 마크가 앱 안 상태 표시(로딩·작업 중)로 그대로 움직일 수 있다.
6. **가족 규칙**: ARA·Sonar 두 마크가 같은 문법이되 실루엣이 다르다(M3 의 "단단함 vs 열림"이 가장 명확).
7. **반복 노출**: 마크는 처음엔 의미가 없다 — 이름 옆에 일관되게 오래 놓여야 고유해진다. 형태 이전에 쓰임 규칙이 필요하다.

## 4. 이야기 (Stage 4) — 3개

### N1. 좌절 이야기 — "터미널 안 AI 는 아무것도 바꾸지 못했다"
- **한 문장**: 터미널에 AI 를 넣어도 일하는 방식은 그대로였고, 그래서 사람과 AI 가 같은 자리에서 일하는 작업대를 만들었다.
- **첫 문장**: "터미널 창 안에 AI 를 넣어 봤다. 아무것도 달라지지 않았다."
- **근거**: 실제 출발점(존재 이유 그대로). ARA 작업대 + Sonar 공동 브라우저라는 구조가 그 답.
- **주인공**: 사내 개발자(준영님) — 직접 겪은 사람.

### N2. 미션 이야기 — "보이는 협업"
- **한 문장**: AI 가 무엇을 하고 있는지 고개만 돌리면 보여야, 사람이 믿고 맡길 수 있다.
- **첫 문장**: "AI 가 일하는 동안, 당신은 무엇을 보고 있었나요?"
- **근거**: AI=인디고·사람=앰버 신호, AI 작업 베일, 승인 카드, 포커스를 뺏지 않는 규칙.
- **주인공**: 팀 — 사람과 AI 둘 다.

### N3. 유산 이야기 — "바다의 옛말과 깊이를 재는 소리"
- **한 문장**: ARA 는 바다, Sonar 는 그 깊이를 재는 소리 — 넓게 일하는 자리와 깊이 들여다보는 창이 짝이다.
- **첫 문장**: "바다를 옛말로 '아라'라고 불렀다."
- **근거**: 두 이름의 실제 뜻, 처음부터 짝으로 설계된 두 제품.
- **주인공**: 두 제품(세계).
- **위험**: 이름 풀이에 그치면 장식이 된다. 시각 방향으로 옮길 때 바다 직역(파도·음파)으로 흐르기 쉽다 — Sonar 세션 거부 목록과 충돌.

**추천**: **N1 을 대표 이야기**(진짜이고, 포지셔닝 P3 와 바로 이어짐), N3 은 이름 소개 한 줄로만.

4. 지금 시안 C 주석의 "브랜드(로고·이름)는 ARA 파랑→핑크" 를 버릴지 — 버리면 신호색 분리가 깨끗해짐
5. Sonar 이름의 SonarSource 겹침 — 사외 공개 계획 여부
