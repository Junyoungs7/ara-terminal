# A.R.A 로드맵 갭 분석 — 더 필요한 것 10선

작성일 2026-08-04. F1~F23 + R1~R8 + Wave 1~5(백로그 M-2~M-8, W2 보안 리뷰 L1~L5까지) 전부 완료된
시점 기준. 4개 관점(실사용·UX / 경쟁 제품 격차 / 운영·배포·신뢰성 / 코드 건전성·기술 부채)을 서로
결과를 공유하지 않는 독립 조사로 각각 수행한 뒤 통합했다. 관점별 원본 초안은
`agent_talk/GAP-UX.md`, `agent_talk/GAP-경쟁제품.md`, `agent_talk/GAP-운영.md`,
`agent_talk/GAP-기술부채.md`에 있다.

**모든 항목은 제출 전 소스 코드로 재확인했다.** 이미 구현된 기능(SFTP, 세션 복원, 포트 모니터,
내장 브라우저, AI 어시스턴트 멀티 프로바이더, MCP 조종 모드, 파일 탐색기 2패널, RDP 프로필, 세션
로그, 명령어 히스토리 등)은 후보에서 제외했다. 방금 끝난 FINAL-batch 라운드에서 처리된 백로그
항목(M-2~M-8, L1~L5)도 갭으로 세지 않았다.

## 한 문단 요약

지금 A.R.A에 가장 부족한 것은 **새 기능이 아니라, 이미 만든 것을 안전하게 오래 쓰고 여러 동료에게
퍼뜨리기 위한 기반**이다. 상위권은 세 갈래로 모인다 — (1) 이미 동작 중인 기능의 **보안·안정성
구멍**(AI 조종 모드가 검증 없이 임의 실행 파일을 셸로 띄울 수 있는 경로, MCP 상태 표시의 유령
세션 누적 버그), (2) **사내 배포를 실제로 떠받칠 인프라의 부재**(자동 업데이트·코드 서명이
전혀 없고, 프로젝트 전체가 로컬 디스크 한 곳에만 존재), (3) **여러 관점에서 동시에 지적된 실사용
공백**(프로필·설정을 다른 PC로 옮길 방법이 없다는 점은 UX·경쟁 제품·운영 세 관점이 독립적으로
모두 짚었다). 그 뒤를 SSH 멀티홉처럼 사내 배스천 환경에서 실제로 막히는 경쟁 제품 대비 공백과,
IPC 핸들러 레이어가 유닛 테스트의 사각지대로 남아 있는 구조적 기술 부채가 잇는다. 즉 "기능이
없어서" 보다 "기능은 있는데 그 기능을 안전하게·오래·널리 쓸 준비가 안 됐다"는 것이 지금 상태의
핵심이다.

### 7. SSH 멀티홉(ProxyJump/배스천 체이닝) 연결을 지원하지 않는다

| 의존성 | 없음(F3 SSH 연결 관리자 위에 얹는 확장). SSH 에이전트 포워딩(10위 밖 후보)과 함께 다루면 효율적. |
| 출처 | 경쟁 제품 격차(`GAP-경쟁제품.md` #1) |

### 8. 코드 서명이 적용되지 않았다

| 구분 | 내용 |
|---|---|
| 무엇이 없는가 | Windows/macOS 정식 코드 서명이 없다. `electron-builder.yml`에 "코드 서명은 MVP 미적용(SmartScreen 경고 수용)", "정식 Developer ID 서명·공증은 배포 직전"으로 명시. macOS는 ad-hoc 서명(`scripts/sign-adhoc.sh`)으로 개발 스모크만 통과. |
| 왜 필요한가(근거) | 계획서(B.6)가 EV/OV 서명을 "배포 직전 도입"으로 못 박아 뒀고 아직 그 시점이 오지 않았다. |
| 없어서 생기는 실제 손해 | 동료가 인스톨러를 받을 때마다 Windows SmartScreen "알 수 없는 게시자" 경고를 넘겨야 한다 — 사내 오피스키퍼 DLP 환경이면 실행 자체가 막힐 가능성도 있다(`USER-CHECKLIST.md` B절 참고). 3번(자동 업데이트)과 결합하면 서명 없는 업데이트는 변조 위험까지 진다. |
| 대략 규모 | 기술 작업량은 소품(빌더 설정)이지만 EV/OV 인증서 구매·조직 신원 확인은 외부 절차라 리드타임이 길다 — 준영님의 의사결정·예산 문제. |
| 의존성 | 3번(자동 업데이트)과 결합 시 우선순위 상승 |
| 출처 | 운영·배포·신뢰성(`GAP-운영.md` #4) |

### 9. 여러 세션에 동시에 같은 입력을 보내는 브로드캐스트 기능이 없다 ★ 2관점 합의

| 구분 | 내용 |
|---|---|
| 무엇이 없는가 | 여러 분할창/탭에 같은 키 입력을 동시에 보내는 기능이 없다(코드 전역에 broadcast류 없음). 입력은 항상 포커스된 세션 하나에만 간다. |
| 왜 필요한가(근거) | 경쟁 제품 관점: MobaXterm(Multi-Exec)·iTerm2(Broadcast Input)·Terminator가 기본 제공하며, 동일 클러스터 여러 노드에 같은 명령을 내리는 운영 작업에서 표준적으로 쓰인다. UX 관점도 독립적으로 "MVP 수락 기준 #3(최대 4분할)이 다중 서버 동시 작업을 전제로 하는데 브로드캐스트가 없다"를 짚었다(다만 UX 쪽은 실사용 불편으로 확인된 근거가 아니라 추측임을 명시했고, 경쟁 제품 관점이 실제 필요성의 근거를 보강한다). |
| 없어서 생기는 실제 손해 | 4분할로 4대 서버를 열어놓고도 같은 명령(재기동·패치 확인 등)을 각 창에 손으로 4번 반복 입력해야 한다 — 분할창 기능의 활용도가 "동시에 보기"까지만 머문다. |
| 대략 규모 | 라운드 하나 — 선택된 세션 집합에 입력 이벤트를 팬아웃하는 로직(PaneGrid/포커스 모델 확장). |
| 의존성 | F4(분할창, 완료) 위에 얹는 확장 |
| 출처 | 경쟁 제품(`GAP-경쟁제품.md` #8) + 실사용·UX(`GAP-UX.md` #9, 추측 명시) |

### 10. 아라(AI) 대화가 앱을 재시작하면 항상 초기화되고 유지할 방법이 없다

| 구분 | 내용 |
|---|---|
| 무엇이 없는가 | 아라 대화 내용을 저장·복원하는 경로가 전혀 없다(F12 세션 로그와는 별개). 앱을 재시작하면 대화가 통째로 사라진다. |
| 왜 필요한가(근거) | `agent_talk/USER-CHECKLIST.md` A-16: "앱 재시작하면 초기화(의도된 동작) / 재시작 후에도 남기길 원하시면 말씀해 주세요" — 준영님 결정이 아직 열려 있는 채로 문서화되어 있다. 소스 확인: `AraSession.ts`·`MainArea.tsx` 어디에도 대화를 디스크에 쓰는 경로가 없음. |
| 없어서 생기는 실제 손해 | 긴 디버깅 대화 중 앱 크래시·업데이트 재시작이 오면 맥락이 통째로 사라져 같은 배경 설명을 매번 다시 해야 한다. |
| 대략 규모 | 라운드 하나 — F12 세션 로그의 마스킹·보존 정책을 재사용해 opt-in 저장 + 복원 UI. |
| 의존성 | F12 세션 로그 인프라(완료) |
| 출처 | 실사용·UX(`GAP-UX.md` #2) |
